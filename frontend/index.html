How It Works

Six design decisions that turned a raw playtime matrix into a game understanding engine.

01

Log-transform playtime

Raw hours are skewed. A user with 5,000 hours dominates the loss. log1p(hours) compresses this into a 0–6.9 range the model can learn from.

02

Latent factor model

Each game and user gets a 50-dimensional embedding vector. The model learns these vectors end-to-end by minimizing prediction error on held-out reviews.

03

Dot product prediction

To predict how much user A will play game B: take the dot product of their vectors plus bias terms. Simple, interpretable, powerful.

04

Weight decay regularization

Without it the model memorizes individual users. wd=0.1 keeps embedding values small, forcing the model to find shared structure across games. PCA variance doubled when we added this.

05

Bias terms

Every game has a bias score separate from its embedding. CS:GO bias=+0.978 means everyone overplays it relative to what genre preference alone predicts.

06

Cosine similarity

Normalize all game embeddings to unit length. Then similarity between two games = their dot product. Portal and Portal 2 score 0.76 — the model never saw genre labels.

Limitations & Transparency

Honest about what the model gets wrong.

⚠

CS:GO similarity is weak

Its userbase is too large and diverse for the embedding to find a clean direction. High bias (everyone plays it) but the similarity vector is noise.

⚠

Dataset bias toward popular games

Filtered to games with ≥200 reviews — meaning the dataset skews toward English-speaking markets and already-popular titles. Niche or non-English games are underrepresented.

⚠

Cold-start problem

New games with few reviews have poor embeddings. The model can't recommend something it has barely seen — a fundamental limitation of collaborative filtering.
